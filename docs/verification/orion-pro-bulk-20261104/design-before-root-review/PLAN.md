# First typed bulk bootstrap — feasibility and bounded local plan

Status: **design for ROOT review, before test or importer implementation**. No database connection, collector, football source read or import has been performed for this study. Only this new evidence folder is written. No change to model `18da43f9…`, sealed 012/013, normalizer/shared helper, old receipt, CI, WORKLOG or application code.

## Decision

A generic clone of sealed tables is **not compatible** with the installed guards. Migration 013 permits one generation owned by the current transaction; inserted retained versions need that draft generation and an open interval; atomic children require the exact parent in its owned draft. Snapshot rows cannot be copied as sealed receipts. The ingest actor has sequence USAGE, not permission to reset them. Source normalizer receipts embed source generation/snapshot IDs. See [013](../../../dashboard/backend/migrations/013_orion_pro_integrity.sql), [role grants](../../../dashboard/scripts/orion_pro_integrity.py) and [source phase receipts](../../../dashboard/scripts/orion_pro_normalize.py).

ROOT accepted the direction **native bulk writer by phase**, with serving held on the old publication until complete acceptance. The proposed first delivery below is deliberately bounded. **It is not yet authorized for implementation or RDS.**

## Exact v1 scope and refusals

Run source-free against two different databases in one owned local PostgreSQL 18.6 cluster. The harness creates its source candidate directly as typed SQL, with no demo correction and no raw bodies. Destination starts with the exact installed 012/013 catalogue, bootstrap generation 1, ten period/position seeds, their two bootstrap contracts and migration journal. Local fixture setup/cleanup may use the harness owner; the importer never receives that administrative session. Application actors are ordinary reader/writer roles with the installed privileges.

The active catalogue has 94 tables / 1,709 columns / 431 FKs: 23 ingest, 61 football, 10 analytics. The proposed input scope has 75 tables: all 61 football relations and these 14 ingest relations: sources, source_datasets, import_runs, source_documents, source_records, document_lineage, resource_fetches, media_assets, match_coverage, relation_contracts, field_contracts, dataset_snapshot_documents, quality_issues, public_aliases. `import_runs` receipts and snapshot-document membership are generated by the native writer, not copied blindly.

Source/destination `dataset_snapshots` and `schema_migrations` are control/baseline relations, not COPY inputs. The ten source analytics tables and seven operational relations—identity_candidates, reconciliation_runs, document_reconciliations, cleanup_items, collection_jobs, asset_jobs, dirty_editions—must be empty in v1. The nine reserved model tables are excluded. All 94 active tables remain checked for target drift; the 75-table count is a transport allowlist, not a redesign or replacement catalogue.

Fail closed before any destination write if:

- Source/destination schema, functions, triggers, privileges, constraints, model or sealed SQL hashes differ from the accepted fingerprints; wrong/old producer or writer transform; mismatched source acceptance/digest; foreign or corrected source candidate; unknown technical JSON contract.
- Any source retained interval is closed (`recorded_to_gen IS NOT NULL`), a phase includes an unsupported change to an existing baseline row, or phase ownership is not fully determined. V1 will **refuse closed history**, not flatten it. A later version may replay closures in their knowledge phase only after separate review/tests.
- Source has a draft/unsealed generation, missing/multiple producer run for a phase, unsupported phase receipt, ready build/publication, published match, model/queue/cleanup/analytics data, unmatched source row, ambiguous self dependency, cycle or dangling reference.
- Destination has any business/operational row outside the exact bootstrap or an already committed **matching bulk prefix**. No conflict overwrite, skip-error COPY or blind ONCONFLICT repair. A different candidate/transform, collision, corrupted receipt or unrelated target row is a refusal.
- Either endpoint is remote, the local cluster is unowned, the two database identities coincide, an application actor is privileged, the destination apply actor is runtime, required grants are absent, or eight-second deadlines/reservation bounds cannot be met. The source actor may be an ordinary reader. No real RDS read is allowed in this local delivery.

## Phases, physical order and cycles

Freeze a source-phase manifest before apply, bound to the complete typed candidate and ROOT's local acceptance. Versioned rows belong to their source `recorded_from_gen`; atomic/append-only children belong to the exact ancestor version's phase. Documents/records/issues/fetches follow their producer run/document lineage. Stable identity/source/dataset/media anchors may be materialized in the first phase under an explicit rule; no versioned fact is backdated. Every eligible source row must have exactly one planned owner; unresolved ownership is a refusal.

Static model analysis found **no inter-table FK cycle and 431 nondeferrable FKs**. Therefore parent tables must precede child COPY commands; this is not a deferred-constraint loader. Three tables with self references need a row-level order: `ingest.sources.upstream_source_id`, competition stage parents and metric numerator/denominator definitions. Reject a cycle/missing parent; do not null a pointer temporarily. The full catalogue order and six atomic-parent edges are in [table-order.json](table-order.json).

Typical phase order: contracts and identity/source/dataset anchors → loader run → document metadata → source records/lineage → entity/dimension versions → editions/matches/team/participant versions → metrics/facts → coverage/network/heatmap parents → their children → snapshot-document membership/loader receipt → seal. The generated FK order, row self-dependency order and trigger parent edges determine the executable order; the prose is not an alternative ordering rule.

## IDs, seeds and sequence gaps

Preserve eligible business logical IDs **and physical revision IDs explicitly**. This avoids an unbounded surrogate crosswalk and preserves all normal FK columns. It is permitted only for the initial empty namespace or an exact matching-prefix resume. Bootstrap seed rows are matched by their full code/definition/version/content contract and not reinserted. Bootstrap snapshot generation/ID are matched semantically; numerical equality between source and target is never assumed.

The catalogue declares 16 sequences and 51 identity columns: 67 sequence providers in total. The commit-generation sequence and generated destination snapshot IDs remain under `begin_generation`; they are never copied/reset. The other 65 business identity/logical-ID sequences need bounded legal catch-up under sequence USAGE when populated: consume `nextval` on the server until its returned value is at least the source maximum. Do this in set-oriented bounded blocks, not one WAN request per ID. Never use setval / ALTER SEQUENCE or move a sequence backwards. If a sequence is already ahead because of a rolled-back attempt, leave it ahead. Require positive increment 1, noncycling, cache 1 and an accepted per-sequence/total reservation ceiling; excessive/sparse source IDs are a refusal, not permission to allocate indefinitely. RO preflight must not call nextval/currval or assume an initial counter. It can bound worst-case advancement from accepted source maxima; apply records actual returned positions under the writer lease. Generation/snapshot sequences are never part of this catch-up.

[PostgreSQL18COPY](https://www.postgresql.org/docs/18/sql-copy.html) accepts provided identity values while retaining triggers/CHECKs. [Sequence functions](https://www.postgresql.org/docs/18/functions-sequence.html) allow nextval withUSAGE and do not undo consumed values on rollback. Explicitly retrying the same source IDs under an empty/matching namespace does not assume that automatically generated IDs repeat. The local E2E must verify the next native insert cannot collide after success or retry.

## New generations, snapshot IDs and honest receipts

For each phase, acquire the existing writer coordination lock, start a real transaction and call `ingest.begin_generation`. Capture the **actual** returned generation and actual inserted snapshot ID. Persist the small source-generation→destination-generation **and** source-snapshot-ID→destination-snapshot-ID mapping in a bounded native bulk receipt. Failed attempts may leave gaps in either namespace.

Only declared generation FK columns and references to `ingest.dataset_snapshots.id` are rewritten using that explicit map. Eligible business IDs remain unchanged. Never recursively rewrite arbitrary numbers in JSON. A later source phase can refer only to mapped earlier/current snapshots; a forward/unknown reference is refused. V1 copies only open intervals.

Use new deterministic bulk snapshot keys bound to candidate/phase/producer/writer fingerprints. Keep each source `import_runs.id` as the explicitly reserved destination run ID so document/run FKs stay exact. Regenerate its `mode`, `status`, `transform_version`, `code_commit`, `started_at`, `finished_at`, `parameters`, `counters`, `checkpoint` and `error` as a bulk execution receipt; bind the original run's full native-row digest, source producer transform and phase membership as provenance. Regenerate `dataset_snapshot_documents.snapshot_id` through the snapshot map, preserving its document membership. These are enumerated control transformations, not a licence to alter business rows. Each technical JSON field must fit its existing 16 KiB contract. The receipt must not claim that the source normalizer ran in the destination, nor copy a source sealed manifest as destination validation proof. Original phase-v2 receipts are source evidence only. Future invocation of the old normalizer is **not** a supported bulk resume path and must require reconciliation rather than silently creating duplicates.

After COPY and the independent phase oracle, finalize the bulk receipt, call `ingest.seal_generation` and commit normally. Existing row triggers, FK/CHECK/UQ and seal/commit validation remain active. No DISABLETRIGGER, replication-role switch, constraint relaxation, superuser/admin grant, new business/staging table, opaque row registry or target legacy-schema access.

## COPY, pipeline and eight-second behavior

Stream typed rows through client RAM into `COPY FROM STDIN` using explicit columns/types. No file-based COPY, COPY PROGRAM, JSON/CSV export, pg_dump or disk payload. Start with row-adapted text COPY to avoid binary width/adapter mismatches; exact Decimal, bool, NULL, empty text, arrays, bytea, timestamps and float round trips must be proved by the oracle. JSONB uses explicit adapters and SQL-null flags so SQL NULL and a permitted JSON null are never conflated; arbitrary embedded numeric IDs are not rewritten. Use deterministic compatible encoding/time/date settings. Business/source timestamps and producer stamps are preserved; only enumerated loader-control fields are regenerated. Document retention/verification timestamps remain source metadata, with no new claim of body verification, provider freshness or purge eligibility.

COPY commands run **outside pipeline mode**; Psycopg does not support COPY in a pipeline. Pipeline may batch independent read/control/reservation queries, then drain/synchronize before COPY. [Psycopg pipeline](https://www.psycopg.org/psycopg3/docs/advanced/pipeline.html) and [COPY adaptation](https://www.psycopg.org/psycopg3/docs/basic/copy.html) document these boundaries. No row-by-row destination INSERT/RETURNING loop is permitted; server-side trigger work per row is retained.

Bound source fetches and COPY chunks by rows/bytes. Each COPY/control/seal/commit command keeps statement_timeout8s and lock_timeout1s; no timeout override or retry that hides a failed phase. Chunking COPY does not promise that final seal/commit validation fits8s. Measure both locally. If a dependency-complete phase cannot seal/commit under that limit, stop and propose smaller **native** phases for review, rather than weakening guards or pretending the whole candidate is atomic. WAN performance remains unmeasured.

The proposed local v1 limits are fixed before the first E2E: at most 64 non-bootstrap phases, 2,000,000 eligible rows overall and 500,000 per table; COPY chunks stop at 1,000 rows or 1 MiB of encoded data, whichever comes first; a single encoded row must fit 1 MiB. Source fetch/COPY payload buffers together may hold at most 16 MiB; bounded row-ownership/self-reference metadata has a separate 32 MiB ceiling and never contains source bodies. Every copied ID must be positive. Reservation is at most 1,000,000 nextval calls per business sequence and 5,000,000 overall, in blocks of at most 10,000 calls. Exceeding a limit refuses the candidate; these are conservative local delivery bounds, not demonstrated real-candidate/WAN capacity. Raising them requires a new reviewed acceptance, never an implicit retry with looser limits.

## Atomicity, restart and no publication

Atomicity is **per native phase**. A failure midway rolls back that phase's rows and receipt; consumed sequence values remain gaps. Prior committed phases remain sealed. Serving stays on the old publication. Do not COPY/build/publish analytics, activate collectors or make new data public.

Apply holds the existing `(20261104,1)` advisory coordination key as a session lease on each database, with acquisition bounded by 1s; each destination phase still uses the normal transaction lock inside `begin_generation`. Freeze the accepted source under one read-only repeatable-read transaction. Recompute source/target fingerprints at apply entry and reject drift or unplanned target rows. The lease coordinates compliant typed writers; target checks remain required. A new process resumes only a verified complete prefix: exact candidate/writer/model bindings, per-phase destination row oracle, snapshot/generation map and seal hashes. A complete matching candidate returns no-op **without nextval, begin_generation or COPY**. A drifted/missing/corrupt receipt refuses before repair. An interrupted phase with no commit is replayed with its fixed explicit business IDs and freshly allocated destination generation/snapshot IDs.
